# 维护者审核清单

CI 只能保证“格式对”，不能保证“代码能用、能信”。下面这份清单是人工审核用的，建议每个 PR 都过一遍。

## 一、先看 CI

- [ ] `validate-submission` 绿灯
- [ ] 只改了 `submissions/`，没有碰 `teams.json`、`index.html`、`teams/`
- [ ] 目录名、版本号、Slug 与 `meta.json` 一致
- [ ] `code.zip` 内 `team.json` 的 name / author / version / team 与 `meta.json` 一致

## 二、再看人

- [ ] 作者能说清代码来源：原创，或附了原作者授权截图
- [ ] 不是把别人的代码改个名字/换个角色就投
- [ ] 版本号合理：修复用修订号，加功能用次版本号，不要每次都 1.0.0
- [ ] 联系方式可用，后续出问题能找到人

## 三、看代码

- [ ] 已实机跑通，`tested` 写了配置、共鸣链、武器、共鸣效率
- [ ] 有视频或截图；没有实机证据的不合并
- [ ] `code.zip` 内没有账号、UID、本机绝对路径等隐私
- [ ] 没有网络请求、文件写入、`eval` / `exec` / `subprocess` 等未说明的调用；有的话要求作者解释
- [ ] 没有嵌套压缩包、可执行文件、混淆代码
- [ ] 脚本能在当前插件版本下正常导入（至少看一遍 import 和入口）

## 四、看描述

- [ ] `description` 能让人复现：起手、循环、什么时候开大、哪些角色要手动
- [ ] 场景 / 难度与实测一致，不是为了曝光乱选
- [ ] 没有夸大宣传（“全角色通用”“无脑满星”这类）
- [ ] 和已有代码的区别写清楚了，避免重复投稿

## 五、决策

- **通过**：打 `accepted` 标签，合并。
- **要改**：打 `needs-author` 标签，指出具体哪一条不过；不要只说“格式不对”。
- **拒绝**：打 `rejected` 标签，说明原因（搬运、无法实机、恶意代码等），关闭。
- **拿不准**：打 `needs-test` 标签，自己实机跑一遍再决定。

## 六、合并后

- [ ] 上传 Release 资产，`assetName` 与 `teams.json` 一致
- [ ] 更新 `teams.json` 的所有派生字段（见 `docs/DATA-CONTRACT.md`）
- [ ] 重新生成 `index.html`
- [ ] 删除 `submissions/` 下的投稿目录
- [ ] 等一次 `sync-downloads`，确认没有 `release assets missing`
- [ ] 在 PR 里回复作者：已发布、下载链接、感谢署名
